# Local Eval Harness

The local `eval-harness` command runs reproducible experiments with Codex CLI and Claude Code using their account
authentication. It records task inputs, interventions, runtime conditions, artifacts, judgments, elapsed time and
available usage. The lightweight project is in `harness/`; it does not require starting NeMo Gym model or resource
servers.

Development acceptance records and the full CLI schema are in `.agents/development/`. These files are for developers;
they are not automatically given to the agents participating in experiments.

## Install from a checkout

The verified local runtime is macOS with Python 3.13.14, uv 0.12.13, standalone Codex CLI 0.154.0 and Claude Code
2.1.270. Node.js/npm is needed to install the two CLIs. The harness checks the CLI versions because its isolation
configuration depends on their behavior. Use the standalone Codex installation below for experimental participants.

These commands install tools inside the checkout and do not change global configuration:

```bash
git clone https://github.com/mashimashica/eval-harness.git
cd eval-harness
python3 -m venv .venv-tools
.venv-tools/bin/python -m pip install uv==0.12.13
.venv-tools/bin/python -m pip uninstall --yes pip setuptools
export PATH="$PWD/.venv-tools/bin:$PWD/.tools/codex/node_modules/.bin:$PWD/.tools/claude/node_modules/.bin:$PATH"
export UV_PYTHON_INSTALL_DIR="$PWD/.tools/python"
uv python install 3.13.14
uv sync --project harness --python 3.13.14 --locked --no-editable
npm install --prefix .tools/codex @openai/codex@0.154.0
npm install --prefix .tools/claude @anthropic-ai/claude-code@2.1.270
codex login
claude auth login
uv run --project harness --no-sync eval-harness --help
```

Authenticate with ChatGPT and Claude subscriptions. The harness copies only account credentials to temporary private
configuration directories and removes them after the call. It strips API/provider environment settings and stops on
failed prerequisites; it does not choose another model or payment route. For a custom credential location, use the
runtime's `settings.auth_source_home` (a configuration directory, never a token in YAML).

Keep the environment exports when opening a new shell. `--no-editable` avoids editable-import problems in synchronized
folders such as iCloud Drive; `--no-sync` uses that installed package. After code changes, run `uv sync --project harness --locked --no-editable --reinstall-package eval-harness`.
For development directly from source, prefix commands with `PYTHONPATH=harness/src`.

## Supported combinations

| Benchmark / operation | Codex CLI | Claude Code |
| --- | --- | --- |
| GDPval task execution and AI evaluation | Supported with native filesystem isolation and Python document libraries | Rejected before execution: the confined file-tool route cannot inspect or generate office-file contents via scripts |
| GSM8K task execution | Supported | Supported with confined Read/Write/Edit/Glob/Grep tools |
| GSM8K mechanical evaluation | No model required | No model required |
| Skill creation from explicit inputs | Supported | Supported for text/Markdown Skills using file tools |
| Saved text scalar or anonymous pairwise evaluation | Read-only judge workspace | Read/Glob/Grep only |

Codex tools can write only to a fresh participant workspace; model tools cannot read account credentials, the development
checkout, or another condition. Evaluation workspaces are read-only. Claude safe/restricted mode disables ambient
instructions, Skills, plugins and shell/network tools. Each selected SKILL.md body is included in the recorded prompt and its supporting files are staged; native discovery is disabled. Claude uses standard context with fast mode disabled. Its reported
USD value is an API-equivalent estimate, not a subscription charge. Keep optional paid overage disabled in your account
when you intend to use only the subscription allowance.

## The six commands

Paths passed on the command line are relative to your current directory. File references inside YAML are relative
to that YAML file. Every command that accepts `--out` requires a new directory.

| Command | Purpose |
| --- | --- |
| `check experiment.yaml` | Validate configuration, inputs, support and authentication without generating or grading. |
| `build build.yaml --out skills/example` | Create a reusable Skill using independently selected creation conditions. |
| `run experiment.yaml --out runs/example` | Select tasks, create optional Skills, execute, save artifacts, evaluate and aggregate. |
| `evaluate runs/example --config judge.yaml --out evaluations/example` | Grade the saved artifacts again; preserve generation identities. |
| `compare runs/example evaluations/example --out reports/example` | Aggregate saved results without calling a model. |
| `resume runs/example` | Continue unfinished work with saved inputs and settings while preserving completed work. |

Prefix these commands with `uv run --project harness --no-sync eval-harness` when using the checkout environment.

## Run a minimal experiment

Prepare the public GSM8K test data with the retained upstream script, then use the supplied configuration:

```bash
uv run --project harness --no-sync python benchmarks/gsm8k/prepare.py
uv run --project harness --no-sync eval-harness check harness/examples/gsm8k-one-task.yaml
uv run --project harness --no-sync eval-harness run harness/examples/gsm8k-one-task.yaml --out runs/first
uv run --project harness --no-sync eval-harness compare runs/first --out reports/first
```

The experiment uses one task and one Codex application call, followed by mechanical grading with no judge model.
Inspect `runs/first/run_manifest.json`, `runs/first/run_state.json`, the saved `evaluations/` directory and
`reports/first/comparison.json`. Each condition/task/repeat has its own logs and deliverable manifest.
Task directory names are safe encoded identifiers; use paths from the journal when writing tooling.

To use Claude for the text task, copy the example YAML and set `application.executor: claude-code`,
`application.model: claude-sonnet-4-6` and `application.settings.reasoning_effort: medium`. Use a new output directory.

For the GDPval audit example, acquire the referenced public spreadsheet separately. Preflight never downloads it:

```bash
uv run --project harness --no-sync python - <<'PY'
```

interpret the resulting AI rubric score as a local diagnostic judgment.

## Create and compare Skills

Creation settings are independent of application and grading. `harness/examples/build-arithmetic.yaml` is a complete
standalone creation example:

```bash
uv run --project harness --no-sync eval-harness build harness/examples/build-arithmetic.yaml --out skills/arithmetic-helper
```

The output directory's basename must match `name`. A successful build contains a validated `SKILL.md`, generated
supporting files and `skill_manifest.json`. The manifest records creation inputs, selected creator Skill versions,
runtime conditions, time, usage and generated file hashes. Private creation logs and frozen inputs live in `.creation/`;
only the generated Skill is supplied during application.

For a skill-creator comparison, save this as `experiments/build-s.yaml`. Replace the Skill paths with directories
containing the versions you intend to study. Paths may be absolute or relative to the YAML file; `~` is expanded.

```yaml
name: word-problems
runtime:
  executor: claude-code
  model: claude-sonnet-4-6
  settings:
    reasoning_effort: medium
    max_turns: 24
    timeout_seconds: 600
prompt: >-
  Create a concise, self-contained Skill for grade-school arithmetic word problems.
  Identify quantities, relationships and units, compute the result, and check it.
  End solutions with a clearly labeled final answer. Do not include benchmark
  problems, gold answers, or grading instructions.
inputs: []
skills:
  - /absolute/path/to/skill-creator
```

Create `experiments/build-a.yaml` with the same brief, inputs and runtime, adding the intended ALPS Skills to `skills`:

```yaml
skills:
  - /absolute/path/to/skill-creator
  - /absolute/path/to/alps/design-process-description
  - /absolute/path/to/alps/design-agent-work-system
```

The harness has no special ALPS branch. Explicitly selected creator Skills form the treatment. Keep development
instructions, benchmark tasks, answers and rubrics out of the creation inputs. Supporting Skill directories retain
their names so relative references between selected Skills work. Creator directory names must be distinct.

After preparing GSM8K, save the following as `experiments/nsa.yaml`:

```yaml
benchmark: gsm8k
tasks:
  path: ../benchmarks/gsm8k/data/gsm8k_benchmark.jsonl
  ids: [gsm8k-0001]
  limit: 1
  seed: 42
repeats: 2
limits:
  max_tasks: 1
  max_retries: 0
  concurrency: 1
application:
  executor: codex
  model: gpt-5.6-luna
  settings:
    reasoning_effort: medium
    timeout_seconds: 300
conditions:
  - id: N
    intervention: null
  - id: S
    intervention:
      path: ../skills/word-problems
  - id: A
    intervention:
      build: build-a.yaml
evaluation:
  method: mechanical
  executor: none
  settings: {}
```

```bash
uv run --project harness --no-sync eval-harness build experiments/build-s.yaml --out skills/word-problems
uv run --project harness --no-sync eval-harness check experiments/nsa.yaml
uv run --project harness --no-sync eval-harness run experiments/nsa.yaml --out runs/nsa
uv run --project harness --no-sync eval-harness compare runs/nsa --out reports/nsa
```

This makes one standalone S Skill, one inline A Skill, and six application calls: the same task repeated twice under
N, S and A. Creation cost is reported separately from repeated application cost. A condition may override
`application.executor`, `application.model` and `application.settings`; an optional `conditions[].intervention.prompt` adds an
explicit recorded instruction. Use equivalent conditions when the intended comparison concerns only Skills.

## Evaluate saved artifacts

A direct evaluation YAML selects `mechanical`, `scalar`, `pairwise` or `human`. It may also appear under the
experiment's `evaluation` field so `run` performs grading and aggregation automatically. When that field is omitted,
the run saves generation results for a later `evaluate` call.

For GSM8K mechanical re-evaluation, save `method: mechanical` and `executor: none` in a new evaluation config.
For scalar AI grading, use the same shape as `harness/examples/gdpval-audit-scalar.yaml`. A scalar judge must return
a JSON object containing only a numeric `score` in [0, 1] and a non-empty `rationale`. Invalid judgments are failures,
not zero scores. Judge settings are independent of application settings.

For an anonymous comparison of N and A, save `experiments/pairwise.yaml`:

```yaml
method: pairwise
executor: claude-code
model: claude-sonnet-4-6
settings:
  reasoning_effort: medium
  timeout_seconds: 300
  max_turns: 12
  pairs: [[N, A]]
```

```bash
uv run --project harness --no-sync eval-harness evaluate runs/nsa --config experiments/pairwise.yaml --out evaluations/nsa-pairs
uv run --project harness --no-sync eval-harness compare runs/nsa evaluations/nsa-pairs --out reports/nsa-all
```

Pairs always match the same task and repeat. The judge receives only `submission_A/`, `submission_B/`, task inputs
and the applicable rubric; condition labels, runtime settings and creator context stay outside its workspace.
Both presentation orders run in separate sessions. Two repeats and one pair require four judge calls. Omitting
`pairs` selects every distinct condition pair, which would require twelve calls for three conditions and two repeats.
The judge returns only `winner` (`A`, `B` or `tie`) and `rationale`. Reports give each condition win credit 1, 0 or
0.5 for a tie and retain both order-specific judgments. Extra votes do not increase the number of generated samples.

## Enter human ratings

Create `experiments/human.yaml` to open an evaluation with no initial ratings:

```yaml
method: human
executor: none
settings:
  ratings: []
  score_scale: {min: 1, max: 5}
```

```bash
uv run --project harness --no-sync eval-harness evaluate runs/nsa --config experiments/human.yaml --out evaluations/nsa-human
```

The initial status is `partial` (exit code 1) because ratings are missing. Append one JSON object per line to
`evaluations/nsa-human/inputs/human_ratings.inbox.jsonl`. This example is **test data**, not a person's quality judgment:

```json
{"rating_id":"fixture-N-0","condition_id":"N","task_id":"gsm8k-0001","repeat":0,"rater_id":"fixture","ratings":{"correctness":5,"clarity":4},"comment":"Example input to verify the rating workflow.","is_test_data":true}
```

Alternatively identify the submission with its full `generation_id`. Use a distinct `rating_id` for each submitted
rating, record the actual `rater_id`, and set `is_test_data: false` only for a real assessment. A human can use any
named numeric criteria; every rating must lie within the declared scale. Comments are preserved verbatim.
Without `score_scale`, criterion values are retained and the normalized aggregate score remains unknown. With a
scale, the mean criterion rating is normalized to [0, 1]; an explicit `score` may supply the overall rating instead.

```bash
uv run --project harness --no-sync eval-harness resume evaluations/nsa-human
uv run --project harness --no-sync eval-harness compare evaluations/nsa-human --out reports/nsa-human
```

Repeat the append/resume operation until the intended submissions are rated. Previous consumed input versions and
completed ratings are preserved; editing consumed inbox text or changing an existing rating identity is rejected.
For a corrected assessment, create a new evaluation. To import an existing JSONL file initially, replace `ratings: []`
with `ratings_path: ratings.jsonl`; its path is relative to the evaluation YAML. Invalid rows are saved separately in
`rejected_ratings.jsonl`. Import and aggregation never call a model.

## Interpret results

Execution completion means that the CLI finished and its outputs were captured. Evaluation completion means that a
grader returned a valid judgment. Task success is a separate result. A failed or missing judgment is not a zero-quality
submission. Missing token or cost measurements remain unknown; a subscription CLI's reported cost estimate is not proof
of a separate charge.

Keep the benchmark, task identity, grading method and sample count attached to every reported result. Re-evaluating an
artifact adds a judgment, not a new generation. Small repeated trials establish that the comparison workflow works;
they do not establish a performance ranking, ALPS superiority, or an official benchmark score.

## Preserve and resume work

Save the complete run directory. The saved configuration and inputs determine resumption, even if the source YAML or
Skill changes later. Use a new run for changed application conditions and a new evaluation directory for changed
grading conditions. Keep human test fixtures labelled as test data; importing ratings is separate from an actual human
quality assessment.

The current scheduler runs serially: `limits.concurrency` must be 1. `tasks.limit` must not exceed the positive
`limits.max_tasks`; `repeats` must be positive and `limits.max_retries` a nonnegative integer. Application attempts
are bounded by that retry count and each runtime's `timeout_seconds`. Each explicit resume invocation may retry
incomplete work; inspect the saved error before resuming a persistent failure. No runtime/model/billing fallback is
performed. The pinned Codex CLI's internal transport retries are contained by the process timeout; Claude native
retries are disabled.

When resuming an evaluation, use its evaluation directory. When resuming a run, use the run directory. Completed
work is reused and failed attempt logs remain available. Preserve the entire directory, including input snapshots and
Skill manifests. Use the manifest and journal paths rather than relying on condition directory names.

If Skill input setup fails before its snapshot is complete, the failure manifest records zero model attempts and
retains the partial setup evidence. Correct the input problem and use a new standalone build output. Inline creations
with a complete frozen snapshot can resume as part of their run.
