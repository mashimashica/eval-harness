# Local Eval Harness

The local `eval-harness` command runs reproducible experiments with Codex CLI and Claude Code using their account
authentication. It records task inputs, interventions, runtime conditions, artifacts, judgments, elapsed time and
available usage. The lightweight project is in `harness/`; it does not require starting NeMo Gym model or resource
servers.

Development acceptance records and the full CLI schema are in `.agents/development/`. These files are for developers;
they are not automatically given to the agents participating in experiments.

Start with [installation](#install-from-a-checkout) and [one task](#run-a-minimal-experiment), then follow the workflow
you need: [Skill comparisons](#create-and-compare-skills), [re-evaluation](#evaluate-saved-artifacts),
[human ratings](#enter-human-ratings), or [resuming work](#preserve-and-resume-work).

## Install from a checkout

The verified local runtime is macOS with Python 3.13.14, uv 0.12.13, standalone Codex CLI 0.154.0 and Claude Code
2.1.270. Node.js/npm is needed to install the two CLIs. Existing installations of these exact standalone CLI versions
may also be placed on PATH. The harness checks the CLI versions because its isolation configuration depends on their
behavior. Use the standalone Codex installation below for experimental participants.

These commands install tools inside the checkout and do not change global configuration:

```bash
git clone https://github.com/mashimashica/eval-harness.git
cd eval-harness
python3 -m venv .venv-tools
.venv-tools/bin/python -m pip install uv==0.12.13
.venv-tools/bin/python -m pip uninstall --yes pip setuptools
export PATH="$PWD/.venv-tools/bin:$PWD/.tools/codex/node_modules/.bin:$PWD/.tools/claude/node_modules/.bin:$PATH"
export UV_PYTHON_INSTALL_DIR="$PWD/.tools/python"
uv python install --no-bin 3.13.14
uv sync --project harness --python 3.13.14 --locked --no-editable
npm install --prefix .tools/codex @openai/codex@0.154.0
npm install --prefix .tools/claude @anthropic-ai/claude-code@2.1.270
codex login
claude auth login
uv run --project harness --no-sync eval-harness --help
```

Authenticate with ChatGPT and Claude subscriptions. The harness copies only account credentials to temporary private
configuration directories and removes them after the call. It strips API/provider environment settings and stops on
failed prerequisites; it does not choose another model or payment route. For a custom credential location, use the
runtime's `settings.auth_source_home` (a configuration directory, never a token in YAML).

Keep the environment exports when opening a new shell. `--no-editable` avoids editable-import problems in synchronized
folders such as iCloud Drive; `--no-sync` uses that installed package. After code changes, run `uv sync --project harness --locked --no-editable --reinstall-package eval-harness`.
For development directly from source, prefix commands with `PYTHONPATH=harness/src`.

## Supported combinations

| Benchmark / operation | Codex CLI | Claude Code |
| --- | --- | --- |
| GDPval task execution and AI evaluation | Supported with native filesystem isolation and Python document libraries | Supported on macOS with `tool_mode: sandboxed_shell`; Bash-only native isolation and a private openpyxl toolchain |
| GSM8K task execution | Supported | Supported with confined Read/Write/Edit/Glob/Grep tools |
| GSM8K mechanical evaluation | No model required | No model required |
| Skill creation from explicit inputs | Supported | Supported using confined file tools or `sandboxed_shell` |
| Saved text scalar or anonymous pairwise evaluation | Read-only judge workspace | Read/Glob/Grep in `files` mode, or read-only Bash in `sandboxed_shell` mode |

Codex tools can write only to a fresh participant workspace; model tools cannot read account credentials, the development
checkout, or another condition. Evaluation workspaces are read-only. Claude safe/restricted mode disables ambient
instructions, Skills and plugins. The `files` mode disables shell/network tools; `sandboxed_shell` exposes only Bash,
for filesystem access, with native enforcement, no network and no unsandboxed fallback. Grading also enables the native
StructuredOutput response tool. Each selected SKILL.md body is included in the recorded prompt and its supporting files are staged; native discovery is disabled. Claude uses standard context with fast mode disabled. Its reported
USD value is an API-equivalent estimate, not a subscription charge. Preflight requires an active subscription and
extra usage disabled; it refuses unconfirmed billing status. It checks exact model selection and effort without
generating a response. Successful account metadata is shared for at most five minutes within one CLI process to avoid
repeated requests for the same account; rate limits remain explicit failures.

The pinned CLI and this account were checked with these exact IDs. Account access can change, so preflight also checks
the current subscription and native selection. No model is substituted when a check fails.

| --- | --- | --- |
| `claude-fable-5-1` | low, medium, high, xhigh, max | Passed at medium |
| `claude-opus-5` | low, medium, high, xhigh, max | Passed at medium |
| `claude-sonnet-5` | low, medium, high, xhigh, max | Passed at medium |
| `claude-haiku-4-5-20251001` | Omit this setting | Passed without effort override |

The existing `claude-sonnet-4-6` ID remains accepted for saved configurations. Model names and native effort options
follow the [Claude Code model configuration](https://code.claude.com/docs/en/model-config). A short availability check
is not a quality measurement or proof that every model/effort combination has been benchmarked.

For the legacy Claude GDPval environment, select `tool_mode: sandboxed_shell`. The shared capability environment described below is an independent opt-in alternative. The harness provides filesystem access only through native Bash
and supplies an isolated `python-openpyxl` command for reading/writing XLSX using the locked openpyxl dependency.
Original reference files, selected Skills and creator inputs are read-only. Application outputs may be written within
the workspace; evaluator workspaces are entirely read-only. Ambient Python packages, account credentials, development
files and other conditions are not tool inputs. Unsupported operating systems or unavailable sandbox prerequisites
are rejected before generation. The `files` route is still useful for text-only work.

After acquiring the reference spreadsheet in the GDPval example below, run the same task with Claude:

```bash
uv run --project harness --no-sync eval-harness check harness/examples/claude-gdpval-audit.yaml
```

The supplied GDPval panel freezes task-specific criteria, including the known prompt/rubric column and entity conflicts, before grading. It keeps independent Sol and Opus findings rather than presenting an official GDPval score. The example makes one application call and two judge calls.

### Shared Office previews for independent judges

Scalar and pairwise AI evaluations can opt into the same visual evidence for Codex and Claude:

```yaml
evaluation:
  method: pairwise
  office_rendering:
    soffice: /absolute/path/LibreOffice.app/Contents/MacOS/soffice
    pdftoppm: /absolute/path/self-contained-poppler/bin/pdftoppm
  judges:
    - id: sol
      executor: codex
      model: gpt-5.6-sol
      settings: {reasoning_effort: max, timeout_seconds: 300}
    - id: opus
      executor: claude-code
      model: claude-opus-5
      settings: {reasoning_effort: max, timeout_seconds: 300, tool_mode: sandboxed_shell}
```

Paths must identify native macOS executables, rather than shell wrappers. LibreOffice must be in an app bundle;
Poppler must have its own `bin` and `lib` prefix with all dependencies inside that prefix. The harness does not install
or update these tools. Its saved renderer identity hashes their complete file trees. Other platforms fail before
conversion; there is no unsandboxed fallback.

Before the first judge call, the harness converts copied DOCX, XLSX and PPTX deliverables into PDF and ordered PNG
pages. A separate macOS sandbox denies network access, reads outside the tool/input roots, and writes to the original
copies. It verifies those restrictions with artificial sentinels and a local network control before conversion.
The converter uses a fresh LibreOffice profile with the highest macro security level.
Macro/embedded-object packages and external resources other than hyperlinks are rejected. Legacy DOC/XLS/PPT and
macro-enabled formats are unsupported. Non-Office deliverables remain available as original files.

`office_renders/` retains the PDFs, PNGs, source hashes, tool identity, conversion commands, timing and failure logs.
`office_renders_manifest.json` and the evaluation manifest bind the saved derivatives. Every judge session receives
the same PNG bytes through native image attachments: Codex `--image` and Claude structured image input. Claude's
Bash-only tool boundary stays in place. Before runtime setup, bounded PNG validation checks complete pixel decoding,
static-image dimensions and checksums; corrupted or animated input is rejected. Each anonymous workspace has `visuals_manifest.json`, mapping image order
and hashes to submission files; native event logs include a redacted image-input receipt. Both presentation orders
reuse the cache. Resume checks hashes and never silently replaces a failed or changed rendering.

Conversion preserves original bytes and mechanical grading. Previews show LibreOffice's interpretation of the saved
print layout: they can differ from Microsoft Office, omit hidden or off-print-area spreadsheet content, and display
recalculated formula values. Use originals for formula/value checks and record unsupported or uninspected details as
unconfirmed. Visual access alone does not establish grading accuracy or completeness.

Each converter subprocess is limited to 120 seconds. Inputs are limited to 50 MiB compressed and 200 MiB expanded;
each document may produce at most 20 pages. PNGs use 120 DPI with a 1600-pixel maximum dimension. A complete judge
request may attach at most 20 PNGs, 5 MiB each and 32 MiB total. Exceeding a limit fails the dependent evaluation;
pages are not silently truncated. Rendering time is separate from model-session usage; it consumes no model tokens.

## Shared GDPval capability environment

Select `settings.environment.profile: gdpval-v1` explicitly for each creation, application and AI evaluation runtime.
This opt-in macOS environment uses the same local MCP tools and copied, locked Python dependencies for Codex 0.154.0
and Claude Code 2.1.270. It is a new experimental environment; existing runs keep their original settings and records.
Do not combine it with `tool_mode` or the legacy evaluation-level `office_rendering` option.

```yaml
settings:
  reasoning_effort: medium
  timeout_seconds: 600
  environment:
    profile: gdpval-v1
    network_domains: [www.bing.com, pypi.org, files.pythonhosted.org]
    office_rendering:
      soffice: /absolute/path/to/soffice
      pdftoppm: /absolute/path/to/pdftoppm
```

Declare the exact research hostnames needed by the selected tasks before execution. The example enables a search
backend and package retrieval only; add the task's research domains to the frozen configuration. Search results outside
that list remain discoverable but cannot be fetched. A blocked domain or inaccessible source is recorded, not silently
replaced with controller-selected research. Wildcards, private addresses, credentials in URLs, non-HTTPS requests,
and redirects outside the list are rejected. Shell processes cannot connect to the network. `search` uses an explicitly
allowed public backend (DuckDuckGo HTML, or Bing RSS when configured); availability and result quality are external
conditions recorded with each request. No API keys or auxiliary AI services are provided.

| Capability | Skill creation | Task execution | Evaluation |
| --- | --- | --- | --- |
| `shell`: bounded code, files and local helper tools | Write own workspace; supplied creation inputs read-only | Write own workspace; supplied references and Skill read-only | Read originals; write and execute inspection copies in `scratch/` |
| Python baseline | Same locked openpyxl, python-docx, python-pptx, Pillow, pypdf, XlsxWriter and transitive packages | Same | Same |
| `search`, `fetch` | Explicit public HTTPS domains | Same; participant performs required research and selection | Same domains when required for evidence |
| `install_wheel` | SHA256-pinned wheel into private task packages | Same; installation time is part of execution | Same, for inspection dependencies |
| `inspect_document` | DOCX revisions/comments, XLSX formulas/PivotTable structure, PDF page count, Office member inventory | Same | Same; structural presence alone is not a functional pass |
| `render_pages`, `view_image` | Selected pages or crop, native image content | Same | Same; frozen common PDFs for independent judges |
| Personal settings, other conditions, grading material | Not staged | Not staged | Only anonymous assigned submissions and declared grading material |

The shell permits one foreground process. Prefix external programs with `exec`, such as `exec python -c 'print(1)'`. Use Python for file operations and sequencing, or separate tool calls; the OS denies child processes, pipelines, subprocesses and background jobs. Invoke `exec soffice ...` separately for copied native conversion. This explicit restriction prevents code from detaching beyond its measured execution boundary. Python runs from a copied private runtime. Wheel installation does not run package setup scripts, rejects unsafe archive
paths and `.pth` files, and never writes global packages. Dependencies requiring system installation or an unsupported
binary platform need an explicitly revised environment. The native LibreOffice/Poppler paths are optional, but required
for rendered inspection. They are hashed with the Python packages, interpreter and harness code. CLI-native shell,
web, plug-ins and autonomous subagents are disabled; file/code operations pass through the shared service. A native
positive/negative sandbox probe must succeed before execution. The supported boundary is macOS Seatbelt; another OS
fails preflight instead of running without isolation.

Both CLIs receive the seven shared work tools. Codex also retains native MCP resource-discovery helpers; the sole
configured service exposes no resources or resource templates. Claude additionally exposes its output-only
`StructuredOutput` formatter when a judgment schema is requested; it grants no file, code or network access. Explicit
MCP settings, empty personal configuration sources and disabled native Skill/plugin discovery control the tool inventory.
Codex limits `enabled_tools` to that seven-tool list and preauthorizes it with `default_tools_approval_mode: approve`.
The service enforces each call's filesystem, public-network and process limits; the CLI keeps `approval_policy: never`.

### Original files, research and inspection evidence

`reference_files/` contains only task-provided materials. A URL that the task asks the participant to investigate is
research, not a supplied file to prefetch. The participant calls `search`/`fetch` and receives retrieved files in
`research/`. The harness preserves requested/final URLs, redirect history, query, timestamp, response status, byte hash,
raw response and tool outcome separately from supplied materials. The exact selection rationale remains in the model
and tool transcript. Evaluation receives only the selected submission's anonymous research evidence, without its
runtime/condition identity.

Saved outputs remain authoritative and unchanged. For inspection, judges use `scratch/` to expand, render, recalculate
or execute copies. The `.harness_evidence/` directory records the environment receipt, effective prompt, tool calls,
full command output, elapsed time, retrieved bytes, derived files, image hashes and requested page/crop ranges. The
manifest is written outside the participant's permission boundary after execution and verified on re-evaluation.
These files are evidence, not submission deliverables. Existing model usage and nullable cost fields still apply;
helper execution and dependency installation are included in elapsed time. Tool failures remain visible in the ledger.

Independent judges share the same saved PDF bytes per source hash. `render_pages` accepts one to four one-based pages
per call with no initial 20-page attachment limit; later pages and regions can be requested as needed. The record
distinguishes available page count from actually viewed pages. A failed conversion stays `unavailable`; the original
remains inspectable and the affected visual criterion remains unconfirmed. A changed source or derivative is an error,
not an invitation to regenerate cached evidence on resume.

### Content, appearance and function are separate findings

AI evaluation with this profile requires explicit, frozen criterion IDs. Criteria that can be checked in the environment
must cite observed evidence. Native PivotTable parts, formulas, validations and revision/comment XML can be inspected;
recalculation and changed-input behavior require actual checks on copies. A screenshot does not establish refresh,
editable Track Changes, audio quality, video timing, or interactive application behavior. Microsoft Office-specific
behavior and perceptual audio/video judgments need an explicitly assigned human or compatible native evaluation path.
They remain unconfirmed until that path is exercised. The current profile supplies no audio/video player or CAD engine.

Native format conversion can reuse saved formula values. A functional check must record changed inputs/selectors and
the resulting dependent values; conversion success alone does not establish recalculation. If needed, invalidate formula
caches and request full recalculation only in the inspection copy, retaining that transformation and its hashes.
Distinguish the AI's reported judgment from the actual inspection trace. A later controller check is separate evidence
and must not be represented as work performed by the original judge.

If any AI scalar criterion is `unconfirmed`, the saved overall score is `null` and `assessment_status` is `unconfirmed`;
the raw judgment and per-item findings are retained. Reports show unconfirmed and failed counts, preserve the planned
sample denominator, and exclude unavailable numbers from arithmetic. They do not turn missing evidence into zero or a
successful assessment. Pairwise `unjudgeable` retains its existing meaning and contributes no win credit.

### Applying an environment change to existing experiments

Freeze task IDs, provided-file hashes, criteria, model/billing route, network domains, dependency/tool versions, time,
concurrency and retry limits before the first session. Keep N/S/A environments equal except for the intended Skill
intervention. The saved environment fingerprint rejects resume after capability code, dependency or native tool changes.
Create a new run for application changes; create a new evaluation identity for changed inspection/criteria when existing
saved submissions and research evidence suffice. Missing participant research cannot be repaired retrospectively by
controller research. Keep the old runs and report the changed protocol separately. Generic capability acceptance is not
proof that a participant solves a task, or that all pages and functional criteria of another task have been inspected.

The development readiness ledger covers all 220 frozen tasks with eight sections per task: identity, primary route,
required capabilities, task-specific checks, Codex/Claude support, assessment methods and inspected scope, evidence,
and inclusion in this acceptance. Current summaries keep content readiness, environment acceptance and acceptance
inclusion independent. A planned method is not an executed check; an unreviewed file, URL or criterion stays unconfirmed.
The earlier content partition is retained in a separate dated historical evidence file and does not constrain current
classifications. Only the two owner-selected tasks enter this acceptance, in their original order; other tasks are not
permanently excluded. Creating an artifact does not establish that its required functional behavior can be assessed.

## The six commands

Paths passed on the command line are relative to your current directory. File references inside YAML are relative
to that YAML file. Every command that accepts `--out` requires a new directory.

| Command | Purpose |
| --- | --- |
| `check experiment.yaml` | Validate configuration, inputs, support and authentication without generating or grading. |
| `build build.yaml --out skills/example` | Create a reusable Skill using independently selected creation conditions. |
| `run experiment.yaml --out runs/example` | Select tasks, create optional Skills, execute, save artifacts, evaluate and aggregate. |
| `evaluate runs/example --config judge.yaml --out evaluations/example` | Grade the saved artifacts again; preserve generation identities. |
| `compare runs/example evaluations/example --out reports/example` | Aggregate saved results without calling a model. |
| `resume runs/example` | Continue unfinished work with saved inputs and settings while preserving completed work. |

Prefix these commands with `uv run --project harness --no-sync eval-harness` when using the checkout environment.

## Create and compare Skills

Creation settings are independent of application and grading. `harness/examples/build-arithmetic.yaml` is a complete
standalone creation example:

```bash
uv run --project harness --no-sync eval-harness build harness/examples/build-arithmetic.yaml --out skills/arithmetic-helper
```

The output directory's basename must match `name`. A successful build contains a validated `SKILL.md`, generated
supporting files and `skill_manifest.json`. The manifest records creation inputs, selected creator Skill versions,
runtime conditions, time, usage and generated file hashes. Private creation logs and frozen inputs live in `.creation/`;
only the generated Skill is supplied during application.

For a skill-creator comparison, save this as `experiments/build-s.yaml`. Replace the Skill paths with directories
containing the versions you intend to study. Paths may be absolute or relative to the YAML file; `~` is expanded.

```yaml
name: word-problems
runtime:
  executor: claude-code
  model: claude-opus-5
  settings:
    reasoning_effort: medium
    max_turns: 24
    timeout_seconds: 600
prompt: >-
  Create a concise, self-contained Skill for grade-school arithmetic word problems.
  Identify quantities, relationships and units, compute the result, and check it.
  End solutions with a clearly labeled final answer. Do not include benchmark
  problems, gold answers, or grading instructions.
inputs: []
skills:
  - /absolute/path/to/skill-creator
```

Create `experiments/build-a.yaml` with the same brief, inputs and runtime, adding the intended ALPS Skills to `skills`:

```yaml
skills:
  - /absolute/path/to/skill-creator
  - /absolute/path/to/alps/design-process-description
  - /absolute/path/to/alps/design-agent-work-system
```

The harness has no special ALPS branch. Explicitly selected creator Skills form the treatment. Keep development
instructions, benchmark tasks, answers and rubrics out of the creation inputs. Supporting Skill directories retain
their names so relative references between selected Skills work. Creator directory names must be distinct.

After preparing GSM8K, save the following as `experiments/nsa.yaml`:

```yaml
benchmark: gsm8k
tasks:
  path: ../benchmarks/gsm8k/data/gsm8k_benchmark.jsonl
  ids: [gsm8k-0001]
  limit: 1
  seed: 42
comparison_design: matched_skills
creation_repeats: 1
repeats: 2
limits:
  max_tasks: 1
  max_retries: 0
  concurrency: 1
application:
  executor: codex
  model: gpt-5.6-luna
  settings:
    reasoning_effort: max
    timeout_seconds: 600
conditions:
  - id: N
    intervention: null
  - id: S
    intervention:
      path: ../skills/word-problems
  - id: A
    intervention:
      build: build-a.yaml
evaluation:
  method: mechanical
  executor: none
  settings: {}
```

```bash
uv run --project harness --no-sync eval-harness build experiments/build-s.yaml --out skills/word-problems
uv run --project harness --no-sync eval-harness check experiments/nsa.yaml
uv run --project harness --no-sync eval-harness run experiments/nsa.yaml --out runs/nsa
uv run --project harness --no-sync eval-harness compare runs/nsa --out reports/nsa
```

This makes one standalone S Skill, one inline A Skill, and six application calls: the same task repeated twice under
N, S and A. Creation cost is reported separately from repeated application cost. A condition may override
`application.executor`, `application.model` and `application.settings`; an optional `conditions[].intervention.prompt` adds an
explicit recorded instruction. Use equivalent conditions when the intended comparison concerns only Skills.

## Evaluate saved artifacts

A direct evaluation YAML selects `mechanical`, `scalar`, `pairwise` or `human`. It may also appear under the
experiment's `evaluation` field so `run` performs grading and aggregation automatically. When that field is omitted,
the run saves generation results for a later `evaluate` call.

For GSM8K mechanical re-evaluation, save `method: mechanical` and `executor: none` in a new evaluation config.
For scalar AI grading, use the same shape as `harness/examples/gdpval-audit-scalar.yaml`. A scalar judge must return
a JSON object containing a numeric `score` in [0, 1] and a non-empty `rationale`, plus item-level findings when explicit
criteria are configured. Invalid judgments are failures,
not zero scores. Judge settings are independent of application settings.

For an anonymous comparison of N and A, save `experiments/pairwise.yaml`:

```yaml
method: pairwise
executor: claude-code
model: claude-opus-5
settings:
  reasoning_effort: medium
  timeout_seconds: 300
  max_turns: 12
  pairs: [[N, A]]
```

```bash
uv run --project harness --no-sync eval-harness evaluate runs/nsa --config experiments/pairwise.yaml --out evaluations/nsa-pairs
uv run --project harness --no-sync eval-harness compare runs/nsa evaluations/nsa-pairs --out reports/nsa-all
```

Pairs always match the same task and repeat. The judge receives only `submission_A/`, `submission_B/`, task inputs
and the applicable rubric; condition labels, runtime settings and creator context stay outside its workspace.
Both presentation orders run in separate sessions. Two repeats and one pair require four judge calls. Omitting
`pairs` selects every distinct condition pair, which would require twelve calls for three conditions and two repeats.
The judge returns `winner` (`A`, `B`, `tie` or `unjudgeable`) and `rationale`, with item findings for explicit criteria. Reports give each condition win credit 1, 0 or
0.5 for a tie and retain both order-specific judgments. Extra votes do not increase the number of generated samples.

## Matched N/S/A panels and uncertainty

For a comparison of Skill methods, add `comparison_design: matched_skills` to the experiment. S and A must use the same
creation model/settings, and N/S/A must use the same application model/settings. Existing Skills need their creation
manifest with matching content, and the S/A creation briefs and input versions must match. When the experiment has automatic evaluation, also set `evaluation.criteria: criteria.yaml` to the
versioned file described below. A suitable configuration to investigate is creation with Sol or Opus 5, application with Luna max, and
independent Sol/Opus 5 judges. This is an experimental configuration, not a claim that Luna max is most efficient.

Use `repeats: 2` with `creation_repeats: 1` to reuse each fixed Skill twice. To measure variation from creating the Skill
again, use `creation_repeats: 2` and reference `build` configs in both S/A conditions. Each creation cohort is an ordinary
run under `cohorts/creation_<index>`; it has distinct Skill creation IDs and the same task IDs. `run`, `evaluate`,
`compare` and `resume` also accept the cohort container. Compare creation cohorts separately from execution repeats.

Before evaluation, create a versioned criteria file. Declare decimal arithmetic, rounding, tolerances, unit convention
and missing-data treatment explicitly. Keep it out of creator/application inputs. This minimal text example can be
saved as `experiments/criteria.yaml` for the GSM8K trial:

```yaml
version: gsm8k-quality-v1
benchmark: gsm8k
policy:
  arithmetic: decimal
  rounding: none
  decimal_places: 0
  absolute_tolerance: 0
  relative_tolerance: 0
  missing: unconfirmed
  units: Preserve the units requested by the problem; the final numeric answer is exact.
tasks:
  '*':
    mechanical:
      - {id: response, description: Saved final response, kind: file_exists, path: agent_response.txt}
    ai:
      - {id: correctness, description: Check the final answer against the benchmark answer and show arithmetic evidence.}
      - {id: clarity, description: Judge whether the explanation is concise and sufficient to verify the answer.}
```

Without explicit criteria, the GSM8K `mechanical` method uses the benchmark's exact-answer grader. Explicit criteria replace that grade with their declared mechanical checks. Explicit machine checks can inspect
JSON numbers, text, workbook sheets/cells, sums and units. Formula execution is disabled: uncached formulas are
unconfirmed or failed according to the declared policy. A quality judgment is stored separately from these checks.
Choose task-appropriate criteria before viewing results; the example is not an official benchmark score definition.

Use `harness/examples/gsm8k-independent-panel.yaml` with its supplied criteria, or save this independent panel as `experiments/panel.yaml`:

```yaml
method: pairwise
criteria: criteria.yaml
pairs: [[N, S], [N, A], [S, A]]
judges:
  - id: sol
    executor: codex
    model: gpt-5.6-sol
    settings: {reasoning_effort: medium, timeout_seconds: 600}
  - id: opus
    executor: claude-code
    model: claude-opus-5
    settings: {reasoning_effort: medium, max_turns: 16, timeout_seconds: 600}
```

```bash
uv run --project harness --no-sync eval-harness evaluate runs/nsa --config experiments/panel.yaml --out evaluations/panel
uv run --project harness --no-sync eval-harness compare evaluations/panel --seed 42 --resamples 1000 --out reports/panel
uv run --project harness --no-sync eval-harness resume evaluations/panel
```

One task, one execution repeat, three pairs, two presentation orders and two judges require 12 judgment calls. A new
evaluation copies saved artifacts and creates no new generation. Each judge sees neither condition labels nor another
judge's result. Win/loss/tie/unjudgeable, order disagreement and judge disagreement remain distinct.

Reports show tie credit 0.5 explicitly. Usable executions are averaged within each task; tasks receive equal weight.
The 95% bootstrap resamples whole tasks with replacement, preserving matched conditions and repeats. Seed, resample
count and aggregation unit are recorded. Repeated votes/order reversals do not add tasks. Fewer than two usable tasks
or identical task scores yield null confidence bounds and a reason. Read judge-specific rates and disagreement
reasons; different criterion versions or judge settings are different protocols. Agreement reports retain the numerator, mutually usable generation-pair denominator, exclusions and disagreement details; a disagreement has no combined numeric score.

Time, token usage and known costs remain separated by creation, application and evaluation. `reported_cost_usd` is
Claude's CLI estimate; actual incremental subscription `cost_usd` is null when unavailable. A reused Skill retains
creation provenance but does not count as a new creation. Evaluation `all_attempts` metrics include archived failed
calls as well as the current judgment; these retries add neither generations nor independent votes. Native structured
JSON responses are validated against the frozen item IDs; invalid results remain failed attempts.

## Enter human ratings

For a `creation_repeats` container, evaluate each `cohorts/creation_<index>` child run separately. The root rejects human input because condition/task/repeat identities would otherwise be ambiguous across creations.

Create `experiments/human.yaml` to open an evaluation with no initial ratings:

```yaml
method: human
executor: none
settings:
  ratings: []
  score_scale: {min: 1, max: 5}
```

```bash
uv run --project harness --no-sync eval-harness evaluate runs/nsa --config experiments/human.yaml --out evaluations/nsa-human
```

The initial status is `partial` (exit code 1) because ratings are missing. Append one JSON object per line to
`evaluations/nsa-human/inputs/human_ratings.inbox.jsonl`. This example is **test data**, not a person's quality judgment:

```json
{"rating_id":"fixture-N-0","condition_id":"N","task_id":"gsm8k-0001","repeat":0,"rater_id":"fixture","ratings":{"correctness":5,"clarity":4},"comment":"Example input to verify the rating workflow.","is_test_data":true}
```

Alternatively identify the submission with its full `generation_id`. Use a distinct `rating_id` for each submitted
rating, record the actual `rater_id`, and set `is_test_data: false` only for a real assessment. A human can use any
named numeric criteria; every rating must lie within the declared scale. Comments are preserved verbatim.
Without `score_scale`, criterion values are retained and the normalized aggregate score remains unknown. With a
scale, the mean criterion rating is normalized to [0, 1]; an explicit `score` may supply the overall rating instead.

```bash
uv run --project harness --no-sync eval-harness resume evaluations/nsa-human
uv run --project harness --no-sync eval-harness compare evaluations/nsa-human --out reports/nsa-human
```

Repeat the append/resume operation until the intended submissions are rated. Previous consumed input versions and
completed ratings are preserved; editing consumed inbox text or changing an existing rating identity is rejected.
For a corrected assessment, create a new evaluation. To import an existing JSONL file initially, replace `ratings: []`
with `ratings_path: ratings.jsonl`; its path is relative to the evaluation YAML. Invalid rows are saved separately in
`rejected_ratings.jsonl`. Import and aggregation never call a model.

## Interpret results

For the minimal experiment, these files are the main entry points:

| File | What to inspect |
| --- | --- |
| `runs/first/run_manifest.json` | Run identity, saved configuration, input and Skill versions. |
| `runs/first/run_state.json` | Each condition/task/repeat, execution status, attempts, metrics and artifact paths. |
| `runs/first/evaluations/<evaluation-dir>/judgments.jsonl` | Saved scores, rationales and evaluation/task-success status. Use the actual evaluation directory reported by `run`. |
| `reports/first/comparison.json` | Generated sample counts and quality/time/usage distributions, separated by evaluation. |

Use the paths recorded in the run journal to find captured deliverables and CLI logs. The execution journal preserves
the generation record; consult the evaluation's judgments for grading completion and task success.

Execution completion means that the CLI finished and its outputs were captured. Evaluation completion means that a
grader returned a valid judgment. Task success is a separate result. A failed or missing judgment is not a zero-quality
submission. Missing token or cost measurements remain unknown; a subscription CLI's reported cost estimate is not proof
of a separate charge.

Keep the benchmark, task identity, grading method and sample count attached to every reported result. Re-evaluating an
artifact adds a judgment, not a new generation. Small repeated trials establish that the comparison workflow works;
they do not establish a performance ranking, ALPS superiority, or an official benchmark score.

## Preserve and resume work

Save the complete run directory. The saved configuration and inputs determine resumption, even if the source YAML or
Skill changes later. Use a new run for changed application conditions and a new evaluation directory for changed
grading conditions. Keep human test fixtures labelled as test data; importing ratings is separate from an actual human
quality assessment.

The current scheduler runs serially: `limits.concurrency` must be 1. `tasks.limit` must not exceed the positive
`limits.max_tasks`; `repeats` must be positive and `limits.max_retries` a nonnegative integer. Application attempts
are bounded by that retry count and each runtime's `timeout_seconds`. Each explicit resume invocation may retry
incomplete work; inspect the saved error before resuming a persistent failure. No runtime/model/billing fallback is
performed. The pinned Codex CLI's internal transport retries are contained by the process timeout; Claude native
retries are disabled.

When resuming an evaluation, use its evaluation directory. When resuming a run, use the run directory. Completed
work is reused and failed attempt logs remain available. Preserve the entire directory, including input snapshots and
Skill manifests. Use the manifest and journal paths rather than relying on condition directory names.

If Skill input setup fails before its snapshot is complete, the failure manifest records zero model attempts and
retains the partial setup evidence. Correct the input problem and use a new standalone build output. Inline creations
with a complete frozen snapshot can resume as part of their run.
