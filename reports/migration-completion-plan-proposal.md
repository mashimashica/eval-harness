# 移行完遂までの実行計画・中間報告案

状態：提案。実装・テスト・追加の技術調査は停止中。この文書の保存は作業再開や既存手順の変更を意味しない。

## 目的と現在地

eval-harnessの生成、成果物の受け渡し、評価、集計、再開をベンチマークに依存しない共通基盤へ移し、互換ラッパーを残さず置換済みの旧専用経路を削除する。原計画のGate Aを最終headで満たすことを完了とする。実モデル実験（Gate B）、merge、release、publishは今回の実装完了に含めず、それぞれ既存の承認条件を維持する。

原計画のPR01・PR03と、PR02の分割分02a・02bは必須CIを通過したDraft PRとして保存されている。PR02cは実装・部分検証中。PR04–11は設計・契約が保存され、実装は残っている。最新のPR02c保存headは2aa8c28b3f074f5e8887fcdccf883123b85199a1。ここにはレビュー済みCursor fixtureの統合と、未完成の共通Cursor CLIテストの準備が含まれる。統合後の全体検証は未実施である。

この案は原計画の11区分と完了条件を維持し、残工程を報告しやすい単位にまとめる。追加のPR分割は、差分の責任が大きすぎるとSolが具体的に示した場合だけ行う。

## 作業量を抑える運用

- 実装は原則1PRずつ、Lunaが1名で所有する。Solは実装可能な既存契約の確認と、まとまった差分の独立レビューを担当する。Astraは全体の責任境界、仕様変更、重要な判断、各節目の受入を担当する。原計画のモデル・努力水準はこの案だけでは変更しない。
- 着手時のタスクは「対象head、目的、変更可能範囲、不変条件、必要検証、出口条件」を短くまとめ、既存契約への参照を使う。後続設計全文を繰り返し再作成・再読する運用を避ける。
- 各作業を原計画の完了条件、または再現できた不具合に対応付ける。新しい機能・一般化・追加の堅牢化が必要になった場合は、その根拠と影響範囲を先に明示する。
- 保存は最大15分以内、または機能単位の編集終了時・テスト開始前のうち早い時点で行う。直接GitHub API、正しいDCO、ref確認、変更ファイルの内容照合を維持し、定型操作を機械化する。モデルが大量の本文・成功ログを再読する必要がない形で照合結果を残す。
- 編集中は変更の影響に対応したテストと静的検査を行う。PR準備時に必要なローカル全チェックとGitHub Actionsを実行し、確定headとの対応を記録する。失敗時は原因に対応した修正・確認を行い、修正後の最終headで必須ゲートを満たす。
- レビューでは具体的な指摘と、その修正差分を追う。変更されていない、すでに確認済みの領域を根拠なく繰り返しレビューしない。新たな根拠が出た場合は再確認する。
- 必須CIは、locked環境、決定論的テスト、Ruff、厳格型検査、厳密な96%以上のカバレッジ、依存関係CVE、秘密情報、著作権、DCOを維持する。対象範囲・閾値・失敗の扱いを弱めない。

## 予算・停止条件

正確な課金トークン量はこの環境から取得できていないため、実作業時間、ツール呼び出し回数、同じ問題への修正・再検証回数も記録する。取得できる利用量があれば併記する。根拠のない消費削減率や全体完了日は約束しない。

初回の提案予算は、M0の調査を30分、PR02cの実装・修正を実作業90分とする。外部CIの待ち時間は別に記録する。この数字は費用の上限を試すための提案であり、90分で必ずPR02cが完了するという見積もりではない。M1の達成時、または上限到達時に、残りの各工程の見積もりと上限を具体化する。全体の予定はPR04の依存問題と隔離環境の実証によって更新する。

次の場合は通常の報告地点を待たず、変更を保存し、追加の実装・調査を停止して報告する。

1. 調査または作業の合意済み上限に達した。
2. 同じ不具合に対する2回の修正・検証で解決せず、同じ方法の継続しか残っていない。
3. 現行の完了条件では解決できない依存・環境上の阻害要因が確認された。
4. 共通契約の変更が複数の後続PRに波及し、手戻りや費用の見込みを大きく変える。
5. 品質ゲートの変更、merge、release、実モデル実験など、現在の実装承認を超える判断が必要になった。

例外報告では、現象、再現・検査の証拠、試した方法、選択肢、推奨案、継続に必要な作業量を示す。原因未確認のまま同じ失敗への試行を繰り返さない。

## 中間報告の定型

詳細報告は一つの短い表を基本とし、次の5項目に限定する。全計画表や長い履歴の再掲は、計画に変更があった場合に行う。

| 項目 | 報告内容 |
| --- | --- |
| 完了した到達点 | PRとhead、出口条件の達成状況 |
| 品質証拠 | 対象head、必須CI、coverageと重要な挙動検証へのリンク |
| 未解決事項 | 件数、影響、次工程を止めるか |
| 作業量・見積 | 実作業時間、呼び出し・修正ラウンド、予算との差、後続見積の変更 |
| 次の工程 | 次の出口条件と適用する予算 |

「保存済み」「部分検証済み」「受入済み」は区別する。進捗は成立した機能と受入条件で示し、テスト件数やPR本数をそのまま工数進捗率へ換算しない。作業中の短報は新しい事実を簡潔に伝え、上記の詳細報告と分ける。
