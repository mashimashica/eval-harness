# 主目的を優先する進行計画の更新案

状態：2026-09-13のユーザー指示に基づく計画変更の提示。今回は実装・検証を再開せず、変更差分だけを記録する。原計画の移行範囲と最終受入条件は維持する。

主目的は、生成・成果物受け渡し・評価・集計・再開を共通基盤へ接続し、互換ラッパーを残さず旧専用経路を削除することである。前案の「NLTKのCVEが未解決なら全体の実装を停止する」というM0条件は、この目的に対して停止範囲が広すぎたため、次のように変更する。

| 対象 | 更新案 |
| --- | --- |
| M0 | 既知の阻害要因を分類する診断として終了する。NLTKの未解決事項だけを理由に、独立して進められる移行作業全体を停止しない |
| PR04のCVE | PR04と、それを含む後続headの受入未解決事項として明記する。必須検査は実行し、失敗は失敗として記録する |
| 後続への着手 | 必要なAPI・挙動・採点意味論・隔離境界が検証できていれば進む。CVEに限った受入保留を、コードの実装を進める条件と区別する |
| 作業の優先順位 | 共通経路の接続、必要な挙動の移植、旧経路削除、第4ベンチマーク受入を優先する。原計画の条件と再現した退行に作業を対応付ける |
| 追加の依存調査 | M0と同じ情報の再調査や、自前のNLTK修正版開発には拡大しない。依存更新と必要な受入検査の時点で状況を確認する |
| 費用・保存 | PR02cの実作業90分上限、反復停止条件、最大15分以内の保存・内容照合、担当分担を維持する |
| 最終完了 | 全必須ゲートを満たすまで「移行完了」と宣言しない。CVEが残れば「機能移行済み・最終受入保留」と明示する |

CVE例外、虚偽のバージョン、監査除外、閾値変更、検査の省略はこの更新に含めない。未受入のPRはDraftとして管理し、mergeしない。後続に必要な機能や境界自体が成立しない場合には、その依存範囲で進行を止める。

実装は原計画の順序を基本として、PR02cの完成、PR04の境界実装、PR05–06の独立評価、PR07–08のStirrup・AA-v2、PR09のN/S/A比較、PR10の旧経路削除、PR11の最終受入へ進める。PR04の受入がCVEだけで保留となった場合も、前提となる契約と機能が検証済みの後続実装は進められる。将来の依存修正で変更が波及したheadは、必要な再検証を行う。

## 報告地点の調整

M1（PR02c）、M3（独立評価）、M4（Stirrup・AA-v2）、M5（N/S/A）、M6（旧経路削除）、M7（最終受入）の区切りは維持する。

M2は「PR04全面受入後」から「grader境界の実装・検証が終わった時点」へ変更する。報告では、コード・機能・境界の検証結果と、CVEを含む受入未解決事項を別々に示す。M3以降も、継承したCVE失敗があるheadをCI成功・受入済みと表現しない。

各報告は、達成した機能、対象headと検証証拠、未受入事項、作業量、次の工程の5項目とする。前工程に進行可能な検証結果があることと、そのPRが全面受入済みであることを混同しない。

次の実作業はPR02cの共通CLI統合テストと全体受入であり、NLTKの追加調査ではない。既知CVEが最終受入を妨げる可能性は残る。その場合も、共通経路の実装と旧経路の削除について、完了した成果と残る受入条件を具体的に提示する。

実モデル実験、merge、release、publishは従来どおり別の承認範囲とする。この更新はそれらを開始する指示ではない。
